# S7 — Error hardening: port, malformed records, `~` paths, `--file` anywhere

## Goal
PRD 8-9: no Python traceback for bad `serve --port` values, malformed task records in the store file, or
other unexpected failures; `~` in store paths expands to the home dir; `--file` works after the subcommand.

## Interface
- `serve --port`: argparse `type=` function accepting integers 0..65535 (0 = ephemeral, as today); anything
  else -> argparse usage error, exit 2, stderr ends with
  `todo serve: error: argument --port: port must be an integer from 0 to 65535, got '<value>'`.
  `_serve` also catches `OverflowError`/`ValueError` from `make_server` -> `error: cannot listen on H:P: <msg>`, exit 1.
- Store load (`TaskStore._check_structure`) additionally rejects, as `StoreError`
  `invalid store file <path>: <why>`: `created` missing or not a str matching `CREATED_RE`
  (why = `task <id> has invalid 'created'`); `due` present and not None/valid date (`task <id> has invalid 'due'`);
  `priority` present and not in PRIORITIES (`task <id> has invalid 'priority'`); repeated id (`duplicate task id <id>`).
  Missing `due`/`priority` keys stay legal (S3 backfill).
- `cli.main` last-resort handler: any other `Exception` -> stderr `error: unexpected <ExcType>: <msg>`, return 1;
  `KeyboardInterrupt` -> return 130, no output. `TodoError` handling unchanged.
- `_resolve_path`: explicit path and `TODO_FILE` both go through `Path(...).expanduser()`.
- `--file` after the subcommand: `cli.build_parser` adds `--file PATH` (dest `file`, `default=argparse.SUPPRESS`)
  to every subparser in `subparsers.choices` AFTER all `register()` calls, so every command (incl. future
  ones such as S8 `edit`) gets it with no per-module change. If given both before and after, the one after wins.
Examples:
- `python -m todo serve --port 99999` -> exit 2, stderr as above, no `Traceback`
- store `{"version":1,"next_id":2,"tasks":[{"id":1,"title":"x","done":false}]}`; `python -m todo --file S export o.csv`
  -> exit 1, stderr `error: invalid store file S: task 1 has invalid 'created'`, o.csv not created
- `HOME=/tmp/h TODO_FILE='~/t.json' python -m todo add A` -> creates `/tmp/h/t.json`; no `./~` dir

## Acceptance
1. `python -m todo serve --port 99999` and `--port -1` -> exit 2, stderr contains
   `error: argument --port: port must be an integer from 0 to 65535`, no `Traceback`; `--port abc` -> exit 2, no traceback.
2. Store file whose task lacks `created`: `list`, `list --json`, `add Z`, `done 1`, `export o.csv` each -> exit 1,
   stderr exactly one line `error: invalid store file <path>: task 1 has invalid 'created'`, store bytes unchanged,
   o.csv absent. Same for `due: 5` / `priority: "urgent"` / two tasks with id 1 (messages per Interface).
3. REST against the store from item 2: `GET /tasks` -> 500 JSON `{"error": ...}` (S4 behavior), server keeps running.
4. Legacy task without `due`/`priority` keys still lists fine (S3 backfill preserved).
5. In-process: patch `TaskStore.list` to raise `RuntimeError("boom")`; `cli.main(["list"])` returns 1, stderr
   `error: unexpected RuntimeError: boom`.
6. With HOME=temp: `TaskStore("~/a.json").path == Path(HOME)/"a.json"`; `TODO_FILE="~/b.json"` CLI `add` writes
   `$HOME/b.json`; `--file "~/c.json" add` writes `$HOME/c.json`; no `~` directory created in cwd.
7. `add T --file X`, `list --file X`, `done 1 --file X`, `rm 1 --file X`, `export o.csv --file X`,
   `import o.csv --file X` behave exactly as with `--file X` before the subcommand; `build_parser().parse_args(
   ["serve","--file","X"]).file == "X"`; `--file A list --file B` reads B; no `--file` -> `args.file is None`.
Preservation: S0 `--version`/usage exit 2; S2 output lines, `error:` exit 1, `--file` > TODO_FILE; S4 port 0,
"port in use" message, SIGINT exit 0; S5 CSV errors; S3 legacy backfill; S1 StoreError for bad JSON/structure.

## Out of scope
`~` in CSV FILE arguments; REST query filtering; CSV header case; changing argparse's usage-error format.

## Depends on
S1 (store load), S2 (cli.main/--file), S3 (due/priority rules), S4 (serve), S5 (export/import commands).

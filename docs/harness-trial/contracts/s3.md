# S3 — Due date + priority, filter/sort in store (and CLI flags)

## Goal
Tasks gain an optional due date (`YYYY-MM-DD`) and a priority (`low`/`normal`/`high`), validated in the
store. `TaskStore.list()` can filter by status and sort by due/priority/created; the CLI exposes this as
`add --due/--priority` and `list --status/--sort`. REST picks the fields up via CREATE_FIELDS/UPDATE_FIELDS.

## Interface
Store (`todo/store.py`):
- Every returned task now also has `"due": str | None` and `"priority": "low"|"normal"|"high"`.
  Tasks on disk lacking these keys (pre-S3 files) are returned with `due=None, priority="normal"`; reads never rewrite the file.
- `CREATE_FIELDS = ("title", "due", "priority")`, `UPDATE_FIELDS = ("title", "done", "due", "priority")`.
- `add(title, *, due=None, priority=None)` — `None` means default (`due` unset, `priority "normal"`).
- `update(id, due=...)` — str sets, `None` clears; `update(id, priority=None)` -> `ValidationError`.
- Validation (`ValidationError`): `due` must be `None` or a str matching `^\d{4}-\d{2}-\d{2}$` that is a real
  calendar date (`2026-02-30`, `2026-1-5`, `"tomorrow"`, `20261201` rejected). `priority` must be exactly one of
  the three lowercase strings (`"HIGH"`, `"urgent"`, `1` rejected). Fields validated before id lookup (as S1).
  Create-path validation lives in `TaskStore._validate_create(title, fields: dict) -> dict` (returns clean
  `{title, due, priority}`; unknown key -> `ValidationError`), used by `add`; S5's import reuses it.
- `list(*, status=None, sort=None)` — `status` in {None, "open", "done"}; `sort` in {None, "created", "due", "priority"};
  anything else -> `ValidationError`. Ordering, always with ascending `id` as the final tie-breaker:
  `None` -> id; `created` -> created asc; `due` -> due date asc, tasks with no due date LAST;
  `priority` -> high, normal, low.
CLI (`todo/commands.py`, S2's module — no new module):
- `add TITLE [--due YYYY-MM-DD] [--priority {low,normal,high}]`; stdout unchanged: `Added task <id>: <title>`.
  Bad `--priority` -> argparse error exit 2; bad `--due` -> store `ValidationError` -> `error: <msg>`, exit 1.
- `list [--status {open,done}] [--sort {due,priority,created}] [--json]` (flags combine; bad choice -> exit 2).
- Text line = S2 prefix `<id> [ ]|[x] <title>` plus, only for non-default values, a suffix
  ` (due YYYY-MM-DD)`, ` (priority P)` or ` (due YYYY-MM-DD, priority P)`. Default task lines are byte-identical to S2.
  Empty (filtered) result -> `No tasks.`. `--json` -> array of full task dicts incl. `due` (null) and `priority`.

Examples:
- `s.add("Pay rent", due="2026-12-01", priority="high")` -> `{"id":1,"title":"Pay rent","done":False,"created":"…Z","due":"2026-12-01","priority":"high"}`
- tasks 1(due 12-05,low) 2(no due,high) 3(due 12-01,normal): `[t["id"] for t in s.list(sort="due")]` -> `[3,1,2]`; `sort="priority"` -> `[2,3,1]`
- `python -m todo --file t.json list --sort due` -> `3 [ ] C (due 2026-12-01)` / `1 [ ] A (due 2026-12-05, priority low)` / `2 [ ] B (priority high)`

## Acceptance
1. `TaskStore(p).add("Pay rent", due="2026-12-01", priority="high")`, then a NEW `TaskStore(p).get(1)` has due "2026-12-01", priority "high"; CLI `list` line 1 is `1 [ ] Pay rent (due 2026-12-01, priority high)`.
2. `add("x")` -> due None, priority "normal"; `add("x", due=None, priority=None)` same.
3. `add` with due `"2026-02-30"`, `"2026-1-5"`, `"tomorrow"`, `20261201` or priority `"HIGH"`, `"urgent"`, `1` raises `ValidationError`; store unchanged.
4. `update(1, due="2027-01-01")`, `update(1, priority="low")`, `update(1, due=None)` persist; `update(1, priority=None)` and `update(99, priority="bad")` raise `ValidationError` (validation before lookup).
5. Pre-S3 file (tasks with only id/title/done/created, written by hand) -> `list()` returns them with due None, priority "normal"; file bytes unchanged after the read.
6. `list(status="open")` / `list(status="done")` partition tasks; `status="all"` or `sort="title"` raise `ValidationError`.
7. Sort fixtures from Interface give due `[3,1,2]`, priority `[2,3,1]`; created sort with equal timestamps (hand-written file) orders by id; `list(status="open", sort="priority")` combines.
8. CLI `add X --due 2026-12-01 --priority low` exit 0, stdout `Added task 1: X`; `--priority urgent` exit 2; `--due 2026-13-01` exit 1, stderr starts `error:`, no traceback, nothing created.
9. CLI `list --status done` with no done tasks -> `No tasks.`; `list --sort bogus` exit 2; `list --status open --sort due --json` -> filtered, ordered array, each element has keys `due` and `priority`.
10. A default task's `list` line equals exactly `<id> [ ] <title>` (no suffix).
11. REST (via S4 `make_server`): POST `{"title":"x","due":"2026-12-01","priority":"high"}` -> 201 with those values; POST/PATCH with `{"due":"bad"}`/`{"priority":"urgent"}` -> 400; PATCH `{"due":null}` -> 200 due null.
Preservation: S1 suite (key-subset checks, unknown-field rejection, id rules, `list()` ascending id); S2 suite (exact `Added/Completed/Deleted` lines, `startswith` list lines, `No tasks.`, exit codes 0/1/2); S4 suite (status codes, `{"error":…}`, `bogus`/`color` keys still 400); S0 both discover forms.

## Out of scope
Descending sort, overdue highlighting, query-string filtering in REST, an `edit` CLI command, time-of-day in due dates.
